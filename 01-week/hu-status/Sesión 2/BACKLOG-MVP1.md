# Backlog inicial · MVP 1 · Multi Tour

Backlog inicial construido en Semana 1 a partir del PDR Multi tour v1.7.1. No sustituye ni reescribe el backlog completo del proyecto: es el corte vertical mínimo razonado para esta sesión.

**Nota de consistencia con documentación posterior.** Este repositorio ya contiene, en `04-week/hu-status/Sesión 2/sprint-mvp1-moscow.md`, una priorización MoSCoW más completa y consolidada del MVP 1. Este backlog inicial de Semana 1 se construyó de forma independiente a partir del PDR, y se usó esa fuente posterior únicamente como referencia de consistencia (no como copia). Las ocho historias siguientes coinciden con el subconjunto `Must Have` de esa fuente posterior; deliberadamente no se incluye una historia de administración de catálogo (creación/edición), porque esa fuente posterior la deja fuera del alcance Must Have del MVP 1 (se apoya en datos mock o seed para la demostración).

## Alcance y dependencias priorizadas

Siguiendo la cadena de dependencias funcionales del PDR: contexto multitenant → identidad/autenticación → catálogo (solo consulta) → cliente → reserva → pago básico. No se incluyen en este corte: administración de tenants vía interfaz, gestión de catálogo por el Administrador, descuentos, ejecución, costos, caja ni devoluciones — son capacidades reales del PDR, pero no forman parte del corte vertical mínimo demostrable de MVP 1.

| ID | Historia de usuario | Prioridad | Criterios de aceptación | Evidencia esperada |
| --- | --- | --- | --- | --- |
| HU-01 | Como plataforma, quiero determinar el tenant activo antes de cualquier operación sensible, para garantizar aislamiento multitenant desde el primer acceso. | Alta | DADO un intento de autenticación o consulta sensible, CUANDO no exista un tenant determinado (enlace, selección explícita o configuración del canal), ENTONCES el sistema debe rechazar la operación en vez de asumir un tenant por defecto. · DADO un tenant inactivo, CUANDO se intente autenticar o reservar sobre él, ENTONCES el sistema debe rechazar la operación. | Contrato `GET /tenants/{tenantId}` documentado + caso de prueba manual mostrando rechazo sin tenant determinado (PASS/FAIL). |
| HU-02 | Como Cliente final, quiero crear mi cuenta dentro de un tenant determinado, para poder iniciar sesión y gestionar mi reserva. | Alta | DADO un tenant activo determinado, CUANDO el cliente se registra con nombre, apellido, correo y contraseña, ENTONCES la cuenta debe quedar asociada exclusivamente a ese tenant. · DADO que el mismo correo ya existe en otro tenant, CUANDO el cliente se registra en el tenant actual, ENTONCES el sistema debe tratarlo como una pertenencia separada, sin mezclar historial. | Contrato `POST /auth/register` documentado + prueba manual con el mismo correo registrado en dos tenants distintos (PASS/FAIL). |
| HU-03 | Como Cliente final, quiero iniciar sesión dentro de mi tenant, para acceder a mi panel y gestionar mi reserva. | Alta | DADO credenciales válidas del tenant determinado, CUANDO el cliente inicia sesión, ENTONCES el sistema debe emitir una sesión válida asociada únicamente a ese tenant. · DADO credenciales inválidas, CUANDO el cliente intenta iniciar sesión, ENTONCES el sistema debe rechazar el acceso. | Contrato `POST /auth/login` documentado + prueba manual PASS/FAIL de login correcto e incorrecto. |
| HU-04 | Como Cliente final, quiero consultar la oferta de tours disponible en mi tenant, para decidir qué reservar. | Alta | DADO un tenant determinado, CUANDO el cliente consulta el catálogo sin autenticarse, ENTONCES debe recibir únicamente los elementos activos y vigentes de ese tenant. · DADO un elemento inactivo del catálogo, CUANDO se consulta la oferta, ENTONCES no debe aparecer en el listado. | Contrato `GET /catalog/services` documentado + prueba manual mostrando catálogo filtrado por tenant y por estado activo (PASS/FAIL). |
| HU-05 | Como Cliente final, quiero crear una reserva con mis datos, mis acompañantes y una modalidad de pago, para adquirir un servicio del tenant. | Alta | DADO un cliente autenticado en un tenant, CUANDO crea una reserva con titular, acompañantes sin documento duplicado y modalidad de pago habilitada, ENTONCES la reserva debe quedar registrada con valor proyectado calculado. · DADO un recurso con cupo limitado sin disponibilidad, CUANDO se intenta reservar el último cupo dos veces de forma simultánea, ENTONCES solo una solicitud debe obtener el cupo y la otra debe recibir respuesta de capacidad insuficiente. | Contrato `POST /reservations` documentado + prueba manual (o script) simulando dos solicitudes simultáneas sobre el último cupo, con resultado PASS/FAIL por solicitud. |
| HU-06 | Como Cliente final, quiero consultar el estado de mi reserva, para saber si está pendiente de pago, confirmada o cancelada. | Alta | DADO una reserva propia, CUANDO el cliente la consulta, ENTONCES debe ver el estado general de la reserva y el estado de pago por separado. · DADO una reserva de otro cliente o de otro tenant, CUANDO se intenta consultar, ENTONCES el sistema debe rechazar el acceso. | Contrato `GET /reservations/{reservationId}` documentado + prueba manual PASS/FAIL de acceso propio vs. ajeno. |
| HU-07 | Como Cliente final, quiero registrar el pago o abono de mi reserva, para avanzar en su confirmación. | Alta | DADO una reserva pendiente de pago con modalidad habilitada, CUANDO el cliente registra un pago o abono válido, ENTONCES el estado de pago debe transitar según las reglas mínimas confirmadas del PDR. · DADO un reintento de la misma solicitud de pago por timeout, CUANDO se reenvía, ENTONCES el sistema NO debe registrar el pago dos veces. | Contrato `POST /reservations/{reservationId}/payments` documentado + prueba manual mostrando un solo registro de pago tras dos envíos de la misma solicitud (PASS/FAIL). |
| HU-08 | Como equipo de desarrollo, quiero un contrato OpenAPI versionado del flujo mínimo, para que los Micro Frontends y servicios backend puedan integrarse sin ambigüedad. | Alta | DADO el alcance Must Have del MVP 1, CUANDO se publica `openapi.yaml`, ENTONCES debe incluir todos los endpoints de HU-01 a HU-07 sin dejar ninguno sin definir. · DADO un cambio posterior de contrato, CUANDO se modifica un endpoint ya publicado, ENTONCES debe quedar versionado y trazable en control de versiones. | Archivo `openapi.yaml` en el repositorio + historial de cambios visible en `git log` sobre ese archivo. |
| HU-09 | Como Administrador de plataforma, quiero que ningún actor pueda consultar o modificar datos de un tenant distinto al suyo, para preservar el aislamiento multitenant en todas las operaciones anteriores. | Alta | DADO dos tenants activos con datos propios (clientes, catálogo, reservas), CUANDO un actor autenticado en el tenant A intenta consultar o modificar un recurso del tenant B, ENTONCES el sistema debe rechazar la operación. · DADO cualquier endpoint de HU-01 a HU-07, CUANDO se ejecuta sin tenant determinado, ENTONCES debe rechazarse. | Matriz de pruebas cruzadas tenant A / tenant B por endpoint, con resultado PASS/FAIL registrado por combinación. |

## Fuera de alcance explícito de este corte inicial

- Modificar, cancelar o reagendar reserva desde autogestión del cliente (el PDR mismo las deja fuera de Fase 1 salvo aprobación documental posterior).
- Devoluciones monetarias operativas completas, caja diaria con cierres, dashboard administrativo mensual y roles opcionales (Gerente/Contador/Analista) con interfaz propia.
- Creación de tenant vía interfaz (el PDR la define como proceso administrativo manual, no como flujo de usuario de MVP 1) y administración de catálogo por el Administrador (se apoya en datos mock/seed para esta demostración).
- Pasarela de pagos, tarjeta, banco o cualquier integración externa de cobro (fuera del alcance de Fase 1 según el PDR).

Estas exclusiones son consistentes con el `Won't Have` ya documentado en `04-week/hu-status/Sesión 2/sprint-mvp1-moscow.md`.
